# ADR-004: PostgreSQL-плейсхолдеры (B3) — scope и план проверки PG-пути

Status: accepted (2026-10-08, лид)

## Context
Blockers B3 (backend, 2026-10-08): все запросы репозиториев (slices 1–6) написаны с
sqlite-плейсхолдерами `?`; pgx v5 stdlib требует `$1…$N` (встроенный QueryRewriter
убран в v5). В окружении нет postgres/docker → e2e-проверка PG-пути невозможна.

Backend тем временем реализовал вариант (б) — `pgx-rewrite` (обёртка pgx stdlib с
трансляцией `?` → `$1..$N`, `internal/database/pgx_rewriter.go`) + CLI
`daemon migrate pg` (ADR-002, дополнение 2026-10-08). Unit-тесты трансляции,
driver registration/open/ping и CLI-обвязку локально — PASS.

## Decision
1. **Реализация** — вариант (б) (wrapper-драйвер `pgx-rewrite`) принят как целевая:
   репозитории остаются на `?` (читаемость, один стиль запросов), диалект
   плейсхолдеров инкапсулирован в одном драйвере.
2. **Scope проверки** — вариант (в): PG **out-of-scope для e2e до появления
   PG-окружения**. Всё, что проверено локально (dev/тесты/live) — на SQLite;
   PG-путь считается реализованным, но **не e2e-проверенным** (пометка в ADR-002).
3. **Критерий готовности PG** (задача на момент появления окружения):
   - `go test ./...` с `DAEMON_DB_DSN=postgres://...` (весь набор, не smoke);
   - live-свип интеграционных тестов frontend (55) против PG-демона;
   - `daemon migrate pg --to ... --from sqlite:...` на реальной БД + проверка
     roundtrip;
   - после зелёного — ADR-002 пометка «e2e-проверено» и закрытие B3 полностью.
4. До этого: в production **не использовать** PG-DSN без прохождения пункта 3;
   ADR-002 остаётся целевой архитектурой.

## Consequences
- Backend не тратит время на PG-окружение «впустую», но и не бросает путь:
  реwriter + migrate уже написаны и покрыты unit-тестами.
- Риск «PG молча не работает» закрыт явным gate (пункт 3) и пометкой статуса.
- Когда появится PG (docker/сервер) — задача одного свипа, без переписывания.
